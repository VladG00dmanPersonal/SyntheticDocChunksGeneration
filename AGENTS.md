# Назначение репозитория

Этот репозиторий предназначен для проектирования промптов, которые генерируют
синтетические документы и наборы чанков с заведомо хорошими, плохими и пограничными
свойствами. Синтетика нужна не для обучения модели, а прежде всего для проверки
чувствительности, направления и диагностической ценности метрик из зависимости
`chunking-metrics`.

Главный результат работы агента — профессиональный, непосредственно применимый prompt
package для генерации синтетики. Не подменяй его общими рекомендациями, отчетом об
исследовании или самим датасетом, если пользователь явно не запросил генерацию данных.

## Источники истины

Перед проектированием или изменением промпта обязательно изучи доступные материалы в таком
порядке:

1. `docs/Examples.md` — локальные положительные и отрицательные примеры чанков.
2. Остальные материалы в `docs/`, включая OCR-текст и JSON, — домен, структура, шум и стиль
   реальных документов.
3. `pyproject.toml` — способ подключения `chunking-metrics`.
4. Документацию и публичный API установленной зависимости `chunking-metrics`. При текущей
   editable-зависимости исходники обычно находятся в `../DocumentChunkingMetricsFramework`;
   не считай этот путь гарантированным и при его отсутствии исследуй установленный пакет.
5. Реализацию метрик и тесты зависимости — только для уточнения фактических контрактов,
   направлений score и необходимых входов.

Не придумывай свойства метрик по их названиям. Если документация, реализация и примеры
расходятся, явно зафиксируй расхождение и следуй фактическому публичному контракту.

Если доступны навыки `generate-synthetic-data`, `prompt-engineering-patterns` или
`llm-evaluation`, используй их как методологическую поддержку. Не устанавливай навыки и не
обращайся к сети без необходимости или разрешения пользователя.

# Что должен получить пользователь

По умолчанию подготовь многостадийный prompt package, а не один монолитный запрос:

1. **Scenario planner** строит контролируемый план покрытия в структурированном виде.
2. **Natural-text generator** по одному сценарию генерирует исходный документ и чанки без
   жесткого JSON-constrained decoding.
3. **Critic/validator** независимо проверяет реалистичность, целевое нарушение, чистоту
   контраста и сохранность нецелевых свойств.
4. **Serializer** упаковывает только принятые примеры и метаданные в JSONL.

Дополнительно дай краткую инструкцию оркестрации стадий: какие данные переходят между ними,
когда пример отклоняется, сколько допустимо повторных генераций и как обеспечить
воспроизводимость. Если среда пользователя допускает только один вызов модели, предоставь
отдельный single-call fallback и честно обозначь ожидаемое снижение разнообразия и надежности.

Каждый промпт должен быть самодостаточным и содержать:

- роль и конкретную задачу модели;
- входные переменные с однозначными именами;
- приоритет источников и правила grounding;
- явные ограничения и запрещенные сокращения пути;
- требуемый формат ответа;
- критерии приемки и процедуру самопроверки;
- минимум один релевантный few-shot пример из локальных референсов и минимум один
  контрпример, если контекстное окно позволяет;
- указание возвращать краткое проверяемое обоснование, но не скрытую цепочку рассуждений.

# Основной принцип генерации

Сначала проектируй пространство отказов, затем генерируй текст. Не проси модель одной
неструктурированной командой «создать хорошие и плохие чанки».

Для каждого тестового случая зафиксируй как минимум:

- проверяемую гипотезу о поведении метрики;
- целевую метрику или совместимый небольшой набор метрик;
- исходный положительный вариант;
- ровно одну основную контролируемую мутацию для отрицательного варианта;
- свойства, которые обязаны остаться неизменными;
- ожидаемое направление изменения score;
- наблюдаемое объяснение, почему именно эта мутация должна вызвать изменение;
- автоматические и смысловые проверки приемки.

Предпочитай контрфактические пары `control` / `treatment`: они должны быть максимально
похожи и различаться главным образом целевым дефектом. После изолированных случаев добавляй
отдельный слой `mixed_stress`, где допустимо сочетать дефекты. Не смешивай эти слои при
анализе чувствительности отдельной метрики.

# Карта свойств и ожидаемых направлений

Используй эту таблицу как начальную гипотезу и сверяй ее с текущей версией фреймворка.

| Свойство | Хороший случай | Плохой случай | Ожидание |
| --- | --- | --- | --- |
| Size Compliance | Размер каждого чанка внутри заданного включительного диапазона | Чанк короче минимума или длиннее максимума | SC выше у хорошего варианта |
| Block Integrity | Границы проходят между абзацами, списками, таблицами и другими блоками | Граница режет один структурный блок | BI выше у хорошего варианта |
| Intrachunk Cohesion | Предложения чанка относятся к одной теме | В чанк внедрена независимая тема | ICC выше у хорошего варианта |
| Contextual Coherence | Чанк тематически соответствует локальному окну документа | Чанк перемещен в чужой локальный контекст | DCC выше у согласованного варианта |
| Coreference Integrity | Антецедент и зависимое упоминание остаются вместе либо ссылка самодостаточна | Местоимение, сокращенная ссылка или зависимое упоминание отделено границей | RC выше у хорошего варианта |
| Boundary Clarity / Logical Independence | Следующий чанк понятен и предсказуем без предыдущего | Следующий чанк начинается с незавершенной зависимости от предыдущего | BC/LI ближе к независимой границе у хорошего варианта |
| Semantic Dispersion | Чанки различимы и взаимодополняемы | Чанки дублируют или почти перефразируют друг друга | SD выше у разнообразного набора |
| ChunkScore | Независимые чанки с низкой избыточностью | Сильные межчанковые зависимости и/или дублирование | ChunkScore выше у хорошего набора |
| HOPE Concept Unity | Один связанный концепт внутри чанка | Несвязанные концепты искусственно объединены | Concept Unity выше у однородного чанка |
| HOPE Semantic Independence | Условия, исключения и определения доступны в том же чанке | Другой чанк существенно меняет ответ или интерпретацию | Semantic Independence выше у самодостаточного варианта |
| HOPE Information Preservation | Все проверяемые факты исходника представлены в чанках без искажения | Значимый факт удален, ослаблен, обобщен или изменен | Information Preservation выше у полного представления |

Не делай вывод, что одна метрика является универсальным oracle качества. В частности:

- высокий SC ничего не гарантирует о семантической границе;
- высокий DCC может сопровождать сильную зависимость от соседей;
- высокий ICC или Concept Unity может быть тривиальным для слишком короткого чанка;
- высокая Semantic Dispersion может возникнуть при чрезмерной фрагментации;
- aggregate-оценки могут скрывать противоположное поведение компонентов.

Для детерминированных формальных свойств разрешено указывать точное ожидаемое значение,
если все необходимые spans и параметры заданы. Для embedding-, perplexity- и LLM-based
метрик не выдумывай точные scores и универсальные пороги: указывай ожидаемое направление,
относительный порядок и возможные confounders.

# Матрица покрытия

Scenario planner должен строить комбинации по осям, связанным с реальными гипотезами отказа.
Базовые оси:

- `quality_class`: `positive`, `negative`, `boundary`, `mixed_stress`;
- `target_metric`;
- `document_structure`: самостоятельный пункт, абзац, список, вложенный список, заголовок,
  таблица или другой реально поддерживаемый блок;
- `boundary_operation`: сохранить, разрезать, склеить, переставить, продублировать, удалить;
- `dependency_type`: нет зависимости, coreference, условие, исключение, определение,
  родительский пункт, дальняя ссылка;
- `semantic_relation`: одна тема, близкие темы, независимые темы, противоречие, дубликат;
- `noise_level`: чистый текст, реалистичный OCR-шум, сильный контролируемый OCR-шум;
- `chunk_size_band`: ниже минимума, минимум, внутри диапазона, максимум, выше максимума;
- `difficulty`: простой, пограничный, композиционный;
- `source_mode`: мутация локального референса, синтез по шаблону референса, новый
  доменно-согласованный пример.

Начни с небольшого набора осей и обеспечь покрытие важных значений. Не перебирай полное
декартово произведение, если комбинации нереалистичны или не проверяют новую гипотезу.
Попроси planner исключать дубликаты и объяснять ценность каждого выбранного tuple.

# Требования к доменной реалистичности

Локальные примеры относятся преимущественно к русскоязычным уставам организаций. Сохраняй
характерные признаки домена: нумерацию пунктов, родительские формулировки, вложенные списки,
юридические условия, исключения и ссылки на ранее определенные сущности.

Учитывай обозначение `||` из `docs/Examples.md` как явный маркер соединения логически
связанных частей в одном чанке, если текущая задача не определяет иной формат.

Плохой пример должен быть правдоподобно плохим, а не очевидно бессмысленным. Тарабарщина,
случайная смена языка и грубые опечатки допустимы только в сценариях OCR/noise. Для проверки
границ, cohesion, coreference или preservation используй содержательно естественные дефекты.

Не копируй персональные, регистрационные и иные чувствительные сведения из реальных
документов. Используй вымышленные организации, имена, даты и реквизиты. Не представляй
синтетический юридический текст как действующий документ или юридическую консультацию.

# Многостадийный workflow

## 1. Анализ контрактов

- Перечисли доступные метрики, их входы, диапазоны и направления интерпретации.
- Отметь, какие метрики уже реализованы, а какие являются планом или требуют отсутствующей
  подготовки данных.
- Определи единицу размера и параметры `min_size` / `max_size` вместо неявных догадок.
- Раздели свойства уровня чанка, границы и всего документа.

## 2. Планирование сценариев

- Сформулируй конкретные failure hypotheses.
- Построй tuples по матрице покрытия.
- Для каждой диагностической пары выбери одну основную мутацию.
- Проверь, что случаи реалистичны для материалов из `docs/`.
- Сбалансируй положительные, отрицательные и пограничные случаи; не генерируй только
  очевидные happy-path и catastrophic-failure примеры.

## 3. Свободная генерация текста

- Передавай генератору один утвержденный scenario tuple за раз либо небольшой однородный
  batch.
- Не заставляй генератор одновременно изобретать taxonomy, писать длинный текст и
  сериализовать сложную JSON-схему.
- Генерируй сначала естественный исходный документ и чанки с простыми устойчивыми
  разделителями.
- Сохраняй факты control-варианта при создании treatment-варианта, кроме факта или границы,
  которые прямо являются целевой мутацией.
- Для Information Preservation всегда сохраняй отдельно исходный документ: одних чанков
  недостаточно для проверки метрики.

## 4. Независимая критика

Critic не должен без проверки принимать самооценку генератора. Он обязан проверить:

- соответствует ли текст domain/style референсам;
- присутствует ли целевая мутация фактически;
- не появились ли дополнительные сильные дефекты;
- сохранились ли заявленные invariant properties;
- правдоподобно ли ожидаемое направление метрики;
- можно ли вычислить необходимые входы фреймворка;
- нет ли почти полных дубликатов других случаев;
- не содержит ли rationale утверждений, которых нет в тексте.

При провале отклоняй пример целиком или регенерируй только дефектное поле. Не «исправляй»
отрицательный пример так, чтобы исчезло намеренное нарушение.

## 5. Детерминированная проверка и сериализация

Где возможно, вычисляй программно длины, число чанков, корректность JSON, наличие пустых
чанков, идентичность дубликатов и сохранение обязательных строк. Семантическое решение не
подменяй одной LLM-самооценкой.

Сериализуй только прошедшие проверку случаи. Один JSON-объект должен занимать одну строку
JSONL; содержимое чанков остается обычным естественным текстом внутри строковых полей.

# Минимальная схема принятого случая

Финальный serializer должен использовать не менее следующего набора полей:

```json
{
  "case_id": "string",
  "pair_id": "string|null",
  "variant": "control|treatment|standalone|mixed_stress",
  "quality_class": "positive|negative|boundary|mixed_stress",
  "source_mode": "reference_mutation|reference_pattern|novel",
  "source_document": "string",
  "chunks": ["string"],
  "target_metrics": ["string"],
  "expected_direction": {"metric_name": "higher|lower|same|uncertain"},
  "primary_mutation": "string",
  "invariants": ["string"],
  "controlled_defects": ["string"],
  "size_policy": {"unit": "characters|words|tokens", "min": null, "max": null},
  "reference_ids": ["string"],
  "oracle_rationale": "string",
  "confounders": ["string"],
  "validation": {
    "schema_valid": true,
    "deterministic_checks": ["string"],
    "critic_status": "accepted|rejected",
    "rejection_reasons": []
  }
}
```

Расширяй схему, если конкретной метрике нужны boundaries, block spans, coreference spans,
context windows, sampled facts или другие подготовленные входы. Не заполняй отсутствующие
аннотации вымышленными координатами. Либо вычисли их из канонического исходного текста, либо
отметь, что требуется отдельная preparation stage.

# Критерии качества prompt package

Перед выдачей результата проверь следующее:

- Все placeholders объявлены и используются последовательно.
- Prompt package применим без чтения твоих пояснений вне самого package.
- Примеры из `docs/` не просто процитированы, а превращены в правила и few-shot contrasts.
- Каждая поддерживаемая метрика имеет хотя бы positive, negative и boundary hypothesis.
- Для ключевых метрик предусмотрены counterfactual pairs.
- Формальные, semantic и document-level метрики не смешаны в один неразличимый label.
- У каждой мутации есть invariants и проверки confounders.
- JSON используется для плана и обмена метаданными, но не ограничивает содержательное
  черновое порождение длинных чанков.
- Предусмотрены разнообразие, дедупликация, отбраковка и ограниченное число retries.
- Указана воспроизводимость: версия промпта, модель, параметры sampling и seed, если провайдер
  его поддерживает.
- Нет обещаний «гарантированного» score для стохастических или model-dependent метрик.
- Итог содержит готовые промпты, а не только описание того, как их когда-нибудь написать.

Приоритет качества выше удобства: допускаются дополнительные model calls, отдельный critic и
ручная выборочная проверка. Однако каждый дополнительный этап должен снижать конкретный риск,
а не добавляться ради сложности.
